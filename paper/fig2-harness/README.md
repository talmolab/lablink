# Fig. 2 — one workshop, start to finish: source audit and generation recipe

**Date:** 2026-09-02  
**Question:** How should the proposed workshop timeline, scaling distributions,
failure/retry rate, and annotated admin-dashboard inset be generated from the
current `taLmolab/lablink` and `taLmolab/lablink-template` implementations?

This note is a source audit, experimental recipe, and executable-harness guide.
The harness is implemented and tested, but it does not claim that the requested
`N = 5, 10, 30, 60` measurements already exist. The audited revisions
are `lablink@8f88ab33262813eb6ed4944a658c9477a2cef829` and
`lablink-template@19b06838acbf40607f079c62bde58dcc7f9e5db3`.

## Bottom line

Generate the figure with the **CLI deployment path** for the top timeline:

```text
lablink configure
  -> lablink deploy
  -> lablink client launch --num-vms N
  -> participants claim seats
  -> export/snapshot all evidence
  -> lablink client destroy
  -> lablink destroy
```

Those are real current commands: the CLI exposes `--num-vms/-n` and a separate
client-fleet destroy command, while full `lablink destroy` first destroys client
VMs and then the allocator
([CLI command definitions](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/app.py#L360-L424),
[full teardown order](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/commands/deploy.py#L786-L879)).

Use `lablink-template` as the pinned infrastructure source and as the documented
alternative deployment path, not as a second implementation of VM allocation.
The template path configures with `./scripts/configure.sh`, deploys with its
GitHub Actions workflow or `tofu apply`, and then operates the same allocator
through `/admin/create`, `/admin/instances`, and `/admin/instances/delete`
([template paths](https://github.com/talmolab/lablink-template/blob/19b06838acbf40607f079c62bde58dcc7f9e5db3/README.md#L21-L32),
[template operations table](https://github.com/talmolab/lablink-template/blob/19b06838acbf40607f079c62bde58dcc7f9e5db3/README.md#L103-L127)).
The current CLI pins template release `v0.3.1` and its tarball SHA-256, so record
that version in the run manifest
([pin](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/__init__.py#L1-L8)).
The template repository itself contains no committed dashboard screenshots; the
stock image assets live in the core repository, while the template links to the
live allocator admin pages
([template admin pages](https://github.com/talmolab/lablink-template/blob/19b06838acbf40607f079c62bde58dcc7f9e5db3/README.md#L103-L118)).

The built-in metrics are necessary but **not sufficient** for the proposed
figure. They provide allocator-deploy phase times and rich final per-VM startup
fields, but final-state export alone cannot reconstruct short-lived status
transitions, the instant a seat became claimable, or evidence that disappeared
before export. Add an external, append-only poller and an event log. No product
code change is required if panel B is defined as the arm-level OpenTofu apply
window. A true per-VM infrastructure-provisioning distribution or strict
availability-zone pinning does require upstream instrumentation/configuration;
the current client Terraform exposes neither a per-instance resource-completion
event stream nor a subnet/AZ input.

## Implemented harness: exact use

The machine-readable contract is `protocol.py`; every collector and analysis
script imports it. The fixed arms are `5, 10, 30, 60`, with three
counterbalanced orders:

```text
replicate 1:  5, 10, 30, 60
replicate 2: 60, 30, 10,  5
replicate 3: 10, 60,  5, 30
```

Run the offline verification first:

```bash
cd paper/fig2-harness
uv run --with pytest --with matplotlib pytest test_fig2.py -q
```

Record the exemplar's one-time configure and deploy phases. The wrapper keeps
an end event and exit code even when the command fails:

```bash
TIMELINE=paper/fig2-harness/data/exemplar-timeline.jsonl
uv run paper/fig2-harness/record_phase.py --events "$TIMELINE" \
  --phase configure -- lablink configure --config /absolute/path/config.yaml
uv run paper/fig2-harness/record_phase.py --events "$TIMELINE" \
  --phase deploy -- lablink deploy --config /absolute/path/config.yaml --yes
```

Before each arm, export the allocator connection information. `IMAGE` must be
the exact digest-pinned value present in `machine.image` in the config. For the
N=60 exemplar, open `/admin/instances` and save the screenshot at the requested
path while the runner waits (three minutes by default):

```bash
export ALLOCATOR_HOST=ec2-…compute.amazonaws.com
export ALLOCATOR_URL=https://allocator.example.org
export SSH_KEY=/absolute/path/lablink.pem
IMAGE='ghcr.io/talmolab/lablink-client-base-image@sha256:…'

paper/fig2-harness/run_arm.sh \
  --arm-n 60 --replicate 1 \
  --image-digest "$IMAGE" \
  --config /absolute/path/config.yaml \
  --template-sha 19b06838acbf40607f079c62bde58dcc7f9e5db3 \
  --instance-type g4dn.xlarge --region us-west-2 \
  --screenshot-path /absolute/path/admin-instances-n60.png
```

Use the same command for every matrix cell, changing only `--arm-n` and
`--replicate`; omit `--screenshot-path` outside the exemplar. If the deployment
is intended to use one AZ, also pass `--actual-az us-west-2a`: the runner asks
AWS for every launched instance's actual placement and fails the arm if it
spans another AZ. Without that flag it still records all observed AZs.

Each run gets a new private directory under `paper/fig2-harness/data/` containing
`meta.json`, append-only `events.jsonl`, VM trajectory, poll health, allowlisted
operation history, claim results, and command logs. Launch, claim, timeout, and
capacity failures are retained; client teardown still runs. No credential or
raw whole-table export is written.

After all arms, record allocator teardown:

```bash
uv run paper/fig2-harness/record_phase.py --events "$TIMELINE" \
  --phase allocator_destroy -- \
  lablink destroy --config /absolute/path/config.yaml --yes --verbose
```

Render only after all twelve arm directories exist. Pass the N=60 arm's event
file as the second timeline source:

```bash
uv run --with matplotlib paper/fig2-harness/plot_fig2.py \
  --data-dir paper/fig2-harness/data \
  --timeline-events paper/fig2-harness/data/exemplar-timeline.jsonl \
  --timeline-events paper/fig2-harness/data/n060-r1-RUN_ID/events.jsonl \
  --dashboard paper/fig2-harness/data/n060-r1-RUN_ID/dashboard.png \
  --out-prefix paper/fig2-harness/figure/fig2-workshop
```

The plotter rejects dry runs/preflight-only runs, invalid collector coverage,
mixed frozen metadata, duplicate or extra cells, wrong chronological order,
and an incomplete 12-arm matrix. It emits a 300-dpi PNG, vector PDF, and
provenance JSON sidecar.

## 1. What LabLink already records

### Allocator deployment

Every `lablink deploy` creates a local JSON record under
`~/.lablink/deployments/` with deployment name, provider, region, template
version, UTC start/end, OpenTofu init/plan/apply durations, allocator health-wait
duration, total machine-work duration, status, and error. Records are written
incrementally, including phase time on exceptions
([schema and persistence](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/deployment_metrics.py#L23-L94),
[deploy instrumentation](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/commands/deploy.py#L425-L575)).

Export it after the run with:

```bash
lablink export-metrics --allocator --format json --output allocator-deploy.json
```

The allocator-only export is local and can still run after the allocator is
destroyed; a combined export produces separate `_client` and `_allocator`
files
([export behavior](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/commands/export_metrics.py#L180-L244)).

### Client provisioning operations

`lablink client launch --num-vms N` posts `num_vms` to `/api/launch`, then polls
the returned operation until it succeeds, fails, is interrupted, or times out
([CLI API client](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/api.py#L173-L254)).
The allocator stores each apply/destroy operation with `created_at`, `started_at`,
`finished_at`, status, parameters, output/error, and resource progress counters;
the authenticated `/api/operations` endpoint returns the 50 most recent rows
([operations schema](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/generate_init_sql.py#L65-L86),
[read endpoint](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/routes/provisioning.py#L284-L318)).

The launch route treats the requested count as an increment: it adds `num_vms`
to the current VM-table row count and applies that absolute count. Therefore,
each scaling arm must begin with an empty client pool; otherwise an intended
`N=10` arm after `N=5` provisions 15 total VMs
([count calculation](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/routes/provisioning.py#L96-L105)).

### Per-VM startup phases

The `vms` table already has absolute start/end times and durations for OpenTofu,
cloud-init, and container startup, plus `TotalStartupDurationSeconds`, status,
health, session start, last heartbeat, and recovery counters
([current schema](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/generate_init_sql.py#L88-L142),
[database guide](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/docs/database.md#L36-L103)).

OpenTofu per-instance timing is produced by `time_static.start/end`, exported as
`instance_terraform_apply_times`, read back by the allocator, and written to the
VM row
([client OpenTofu timers](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/terraform/main.tf#L5-L7),
[timer derivation](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/terraform/main.tf#L178-L218),
[output](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/terraform/outputs.tf#L35-L45),
[database write](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/routes/provisioning.py#L156-L169)).

Important provisioning caveat: `time_static.end` depends on the complete
`aws_instance.lablink_vm` collection, not on instance `i`. The exported
"per-instance" durations therefore share the arm's all-instances-complete
boundary and must not be presented as independent EC2 provisioning completion
times. For the unmodified product, panel B should use the apply operation's
`started_at -> finished_at` duration across arm replicates. If true per-VM
provisioning times are required, timestamp each named `aws_instance` completion
line in the allocator's streamed OpenTofu output (or collect equivalent AWS
events) and persist those append-only timestamps.

Cloud-init posts its start/end/duration after starting the container and polling
for `status=running`; the container posts its own start/end/duration after
launching KasmVNC, XFCE, the agent, and monitoring workers
([cloud-init measurement](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/terraform/user_data.sh#L197-L238),
[container readiness/status](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/client/start.sh#L666-L706),
[container measurement](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/client/start.sh#L756-L769)).

Important measurement caveat: do **not** use
`TotalStartupDurationSeconds` as the end-to-end wall clock for panel C. The
database computes it as `tofu + cloud-init + container`, but container startup
occurs inside the cloud-init interval, so that sum overlaps time
([sum implementation](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/db/vms.py#L1146-L1165),
[container is launched within user data](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/terraform/user_data.sh#L137-L204)).
Use the external launch timestamp to first observed `status=running`, or the
absolute `ContainerEndTime` after checking clock offsets.

### Seat claims

A participant claims a seat by `POST /api/request_vm` with only an email. A
fresh request atomically selects a running, unassigned, non-unhealthy,
non-admin-reserved VM; concurrent claims use `FOR UPDATE SKIP LOCKED`, and a
successful browser-session preparation writes `SessionStartedAt=NOW()`
([participant route](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/routes/public.py#L32-L72),
[atomic assignment](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/db/vms.py#L631-L684),
[session timestamp](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/client_session.py#L118-L132)).
The real-database test verifies that simultaneous requesters receive distinct
VMs
([concurrency test](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/tests/db/test_vms.py#L945-L995)).

For the figure, `UserEmail != NULL` or `SessionStartedAt != NULL` means a seat is
claimed. Do not use the dashboard's `In Use` column as the claim indicator:
`InUse` means the configured subject software is active, and a participant may
already own a seat while it remains false
([semantics](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/docs/database.md#L116-L123)).

### Failure and retry evidence

The durable per-row recovery fields are `reboot_count` and `last_reboot_time`.
The auto-reboot service checks failures once per minute by default, permits up
to three attempts with a five-minute cooldown, and increments `reboot_count`
when SSH reboot or EC2 stop/start is initiated
([defaults and loop](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/reboot.py#L24-L81),
[recording a reboot](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/reboot.py#L224-L280)).
Custom startup scripts also have configurable retry attempts and exponential
backoff, but those attempts are currently observable in container logs, not a
dedicated numeric VM-table column
([retry loop](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/client/start.sh#L388-L448)).

## 2. Why an append-only collector is required

The normal client export is a snapshot of every current VM row, not an event
history
([export query](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/db/vms.py#L147-L171)).
`lablink client destroy` clears the VM table after destroying the client
workspace, and full `lablink destroy` removes the one-use allocator database
([clear after destroy](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/routes/provisioning.py#L229-L260),
[database lifetime](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/docs/database.md#L30-L39)).
Consequently a final CSV cannot show when a VM first changed to `running`, a
transient `error`/`Unhealthy` state, or a row that disappeared before export.

Add these paper-support scripts (preferably in `lablink-paper-figures`, whose
existing convention separates immutable raw data, processed data, analysis,
and plotting):

1. `scripts/analysis/run_fig2_arm.sh` — write an append-only UTC JSONL event for
   command start/end/exit status; invoke launch, claim burst, exports, client
   destroy, and allocator destroy. Never delete a prior arm.
2. `scripts/analysis/poll_fig2_allocator.py` — every 2–5 seconds fetch
   `/api/operations` and query only the allowlisted VM columns (for example with
   the allocator-host SSH/`psql COPY (SELECT ...)` path), then append one row per
   VM plus one row per operation with collector timestamps. Continue through
   transient request errors and log a `poll_error` event. Avoid using
   `/api/export-metrics` as the polling source unless the response is filtered
   in memory without ever persisting the unfiltered payload: that endpoint
   currently returns credential-bearing columns too.
3. `scripts/analysis/claim_fig2_seats.py` — issue a synchronized burst of N
   unique synthetic emails (or log real workshop requests), retain response
   code and latency, and keep cookies only in an ephemeral directory.
4. `scripts/analysis/process_fig2.py` — validate schema/run metadata, derive
   per-VM provisioning and readiness times, arm-level all-ready time, claims,
   retries, and failures, then emit small de-identified processed CSVs.
5. `scripts/plotting/plot_fig2_workshop.py` — generate both PDF and 300-dpi PNG,
   plus a metadata sidecar containing git SHAs, config hash, image digest,
   instance type, AMI, region, poll interval, timeout, and replicate count.

The API collector is preferable to scraping the HTML. It should retain at least:

```text
poll_time_utc, arm_n, replicate, hostname,
status, healthy, reboot_count, last_reboot_time,
tofuapplystarttime, tofuapplyendtime, tofuapplydurationseconds,
cloudinitstarttime, cloudinitendtime, cloudinitdurationseconds,
containerstarttime, containerendtime, containerstartupdurationseconds,
createdat, sessionstartedat, last_seen_at,
operation_id, op_type, operation_status, operation_created_at,
operation_started_at, operation_finished_at, resources_completed,
resources_total, operation_error
```

Record a run manifest before every arm: LabLink SHA/version, template
SHA/version, client and allocator image digests (not mutable tags), config hash,
startup-script hash, AMI, EC2 instance type, AWS region/AZ, replicate, intended
N, UTC start, poll interval, ready timeout, and operator/allocator/VM clock
offset probes. Keep all of those fixed across N except the intended VM count.

Security/privacy caveat: the current export code discovers every VM-table
column automatically and warns that newly added sensitive columns must be
filtered explicitly
([warning](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/routes/metrics.py#L144-L194)).
The table currently includes email, browser token, VNC password, and credential
fields. Use `umask 077`, do not commit raw exports, select only the allowlist
above, hash or discard emails, and redact the address bar/emails in screenshots.

## 3. Experimental runbook

### A. Freeze the deployment

1. Create a dedicated AWS deployment and record both repository SHAs.
2. Pin the allocator image, client image **digest**, AMI, instance type, region,
   startup script, repository input, and networking/DNS mode. The template
   configuration owns these machine/image/region inputs
   ([config example](https://github.com/talmolab/lablink-template/blob/19b06838acbf40607f079c62bde58dcc7f9e5db3/lablink-infrastructure/config/config.yaml#L17-L43)).
   The current `MachineConfig` and client Terraform have no subnet or AZ field.
   Either add and document a `subnet_id` input end to end, or record the actual
   AZ of every instance and describe the run as region-pinned rather than
   AZ-pinned. An `AZ=...` shell variable by itself changes nothing.
3. Confirm EC2 quota and budget for the 60-VM arm before provisioning.
4. Use at least three independent repetitions per N (five if budget permits).
   Per-VM points are correlated within an OpenTofu apply, so show both VM-level
   distributions and arm-level summaries instead of treating all VMs as
   independent replicates.

### B. Capture the exemplar workshop timeline

Use one real, representative run (for example N=30) for panel A. Record these
events in one UTC JSONL file:

```text
configure_start -> configure_end
deploy_start -> allocator_healthy
launch_requested(N) -> tofu_apply_finished
first_vm_ready -> all_vms_ready
first_seat_claimed -> last_seat_claimed
client_destroy_start -> client_destroy_finished
allocator_destroy_start -> allocator_destroy_finished
```

`lablink configure` writes the config and automatically performs AWS state
setup; `lablink deploy` downloads the pinned template, runs init/plan/apply, and
waits on allocator health
([configure behavior](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/app.py#L122-L203),
[deployment guide](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/docs/cli/first-deployment.md#L84-L112)).
Keep human prompt time visible as a separate pale segment or exclude it with an
explicit legend; the native allocator total deliberately sums machine phases
and excludes confirmation time
([definition](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/commands/deploy.py#L464-L566)).

### C. Run the scaling arms

For each `N in {5, 10, 30, 60}` and each replicate:

1. Assert the VM table is empty and no operation is queued/running.
2. Start the poller and record `launch_requested` on the same collector clock.
3. Run `lablink client launch --num-vms N --verbose`, retaining stdout/stderr
   and exit status.
4. Continue polling until every intended VM has first reached `running` and has
   a non-null container end time, or until a predeclared timeout (recommend 15
   minutes, matching the workshop guide's warning threshold plus margin).
5. Claim seats only after the pool is ready. For a synthetic load test, issue N
   concurrent `POST /api/request_vm` requests with unique non-real emails; for
   the exemplar real workshop, use the observed `SessionStartedAt` range.
6. Capture the live `/admin/instances` screenshot.
7. Stop the poller cleanly and explicitly export both metric sources **before**
   destroying clients:

   ```bash
   lablink export-metrics --client --allocator --format json \
     --output "fig2-N${N}-rep${REP}.json"
   ```

8. Snapshot `/api/operations`, then run `lablink client destroy --yes --verbose`.
   Wait for its destroy operation to finish and verify the pool is empty before
   the next arm.
9. After the final arm and after copying all evidence, run
   `lablink destroy --yes --verbose`. Although full destroy offers a final
   combined export, an export failure is caught and teardown continues, so do
   not rely on that as the sole copy
   ([pre-destroy export behavior](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/cli/src/lablink_cli/commands/deploy.py#L841-L879)).

For a template/GitHub-Actions deployment, destroy clients through the live
allocator UI/API before triggering the full infrastructure-destroy workflow.
At the audited revision the allocator stores client state under
`{deployment_name}/{environment}/client/terraform.tfstate`, but the template's
destroy workflow still probes the older `{environment}/client/terraform.tfstate`
key and marks that step `continue-on-error`; it can therefore miss current
client state
([allocator state key](https://github.com/talmolab/lablink/blob/8f88ab33262813eb6ed4944a658c9477a2cef829/packages/allocator/src/lablink_allocator_service/main.py#L344-L368),
[template destroy step](https://github.com/talmolab/lablink-template/blob/19b06838acbf40607f079c62bde58dcc7f9e5db3/.github/workflows/terraform-destroy.yml#L61-L109)).

### D. Definitions fixed before analysis

Use these definitions in the script and caption:

| Quantity | Definition |
|---|---|
| Provisioning time, per arm (current product) | Apply operation `finished_at - started_at`; show its distribution across independent arm replicates. |
| Provisioning time, per VM (requires added instrumentation) | Timestamped completion of that named `aws_instance` minus the arm's apply start; do not substitute the current shared `time_static.end` values. |
| Seat-ready time, per VM | Collector time of first observed `status == running` minus collector `launch_requested`; uncertainty is at most one poll interval. |
| Fully initialized time, per VM | `ContainerEndTime - launch_requested`, only after correcting/validating clock offset. |
| All-ready time, per arm | Maximum seat-ready time across all N intended VMs; failed/never-ready arms remain failures, not a max over survivors. |
| Seat claim | First non-null `SessionStartedAt` (or first observed `UserEmail`); never `InUse`. |
| Retry | Increase in `reboot_count`; report startup-script retries separately if parsed from logs. |
| VM failure | Intended VM never reaches ready before the declared timeout, or terminates/disappears before ready. |
| Operation failure | Apply/destroy operation status is `failed` or `interrupted`; keep separate from VM failure. |
| Retry rate | VMs with at least one recovery attempt / intended VMs, with numerator and denominator shown. |
| Failure rate | Never-ready intended VMs / intended VMs; additionally report failed arms / attempted arms. |

These definitions prevent three common errors: calling `InUse` a seat claim,
double-counting overlapping startup phases, and dropping never-ready VMs from
the time-to-ready distribution.

## 4. Figure construction

  teardown as distinct colored intervals. Put exact wall times above each
  interval; show human wait/workshop duration with a light treatment so it

## 5. Acceptance checks before publication

- Every arm has exactly N distinct intended hosts and an empty pool at start.
- Every derived value traces to an immutable raw event/snapshot and run manifest.
- Poll gaps and clock offsets are within declared tolerances.
- Never-ready and disappeared hosts remain in denominators.
- Client metrics, operation history, and screenshot are captured before client
  teardown; allocator-deploy metrics are copied before or after full teardown.
- Raw exports are permission-restricted, uncommitted, and scrubbed of emails,
  browser credentials, tokens, passwords, and logs before processing.
- The plot script regenerates both PDF and PNG from processed data without
  reading private raw data.
- The caption distinguishes the real exemplar workshop timeline from synthetic
  or repeated scaling arms.
